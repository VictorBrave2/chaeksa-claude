# 책사 아키텍처 — 무엇을 코드가 정하고, 무엇을 LLM이 쓰는가

## 원칙
> **뼈대는 코드가 정하고, 문장은 LLM이 쓴다.**

가설·순위·확률·실행과제·간지를 LLM이 만들게 두면 같은 사주라도 날마다 다른 말이 나온다.
그 순간 신뢰가 무너진다. 그래서 판단은 전부 규칙으로 확정하고, LLM에게는 그것을 사람의 말로
옮기는 일만 맡긴다.

## 3단 구조

```
① 분석엔진 (결정론적, AI 없음)
   astro.js   태양 황경(VSOP87) → 절기 시각
   lunar.js   삭 + 무중치윤법 → 음력 변환
   places.js  출생지 경도 · 표준시
   engine.js  표준시·진태양시 보정 → 원국 4주 · 대운
              analyze() → 십신 · 지장간 · 오행 분포 · 강약 · 용신 후보
        ↓ 구조화된 데이터

② 통변엔진 (결정론적, AI 없음)
   tongbyeon.js + rules-*.js
   frame()     질문 → 도메인·시기 판별 → 6D 스택 → 형충회합·조후 보정
               → 경쟁 가설 2개(사전확률) + 판별 질문 3개
   revise()    사용자 답변 → 우도비 → 사후확률 (Belief Revision)
   decide()    확신도·미확인·변동성·전환 → 선택지 A/B/C 점수
   dayFrame()  오늘 일진 → 결·주의·행동·시간대 확정
   calendar.js 택일 점수 / compat.js 궁합 점수
        ↓ 확정된 판단

③ 통변 LLM (서술만)
   ai.js
   deepNarrate()  프레임 + 답변 + 선택지 + 기록된 지표 → 상담문
   dailyBrief()   dayFrame → 아침 브리핑
   chat()         dayFrame + 고정 원국 해석 → 대화
   compatText()   궁합 규칙 결과 → 관계 서술
   가드: "새 가설 금지 · 순위와 확률 그대로 · 간지는 주어진 것만 · 재계산 금지"
   후처리: dehanja() 한자를 한글로 (첫 괄호 표기 하나만 남김)
```

## 예외 — 코드가 정하지 않는 곳
| 항목 | 누가 정하나 | 이유 |
|---|---|---|
| 신강·신약, 용신, 격국 | **LLM** (buildProfile) | 계산기의 단순 개수 세기보다 낫다고 판단. 다만 **처음 한 번만 만들어 고정**하고, 이후 모든 브리핑·상담이 그 값을 따른다 |
| 택일 | 규칙만 (LLM 없음) | 날짜 점수는 서술이 필요 없다 |

`engine.analyze()`도 강약을 계산하지만, 최종 판단은 고정된 원국 해석을 따른다.
두 값이 어긋나 보일 수 있으므로 화면에는 고정 해석을 우선 노출한다.
